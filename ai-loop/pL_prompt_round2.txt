# 1라운드 검증 결과

[1] tieredTotal 구간 경계 → **기각**
    코드가 이미 소득세 누진공제 방식입니다:
      for (const t of tiers) { if (participants < t.min) continue;
        const countInBracket = Math.min(participants, t.max) - t.min + 1;
        total += Math.round(unitBase * t.factor) * countInBracket; }
    각 구간 인원수만큼만 그 구간 계수를 적용해 합산하므로 인원 1명 증가 시 추가액이
    항상 0 이상입니다. 추가로 불변식 퍼징 52,360건(목적지 55 × 인원 17 × 일수 14 ×
    출발일 4)에서 총액 단조성 위반 0건, 인원 1명 증가 시 1인당 +15% 초과 점프 0건.

[2] getLeadTimeFactor 타임존 → **실사용 환경에서는 기각**
    실측(TZ=Asia/Seoul, offset -540): 0/1/2/30/90/200일 뒤 전부 정확히 0/1/2/30/90/200.
    이유: new Date('YYYY-MM-DD')는 UTC 자정, today는 로컬 자정이라 차이가 항상
    (offset)시간만큼 고정 오프셋이고 KST(+9)에서는 0.375일이라 Math.round가 흡수합니다.
    UTC+12 이상에서만 하루가 밀립니다. 고객은 전원 한국이라 현재는 영향 없음.
    → 이 판단이 틀렸다면 KST 기준으로 어긋나는 구체적 날짜를 제시해 주세요.

[3] 클라이언트 계산 금액을 서버가 그대로 저장 → **인정. 별도 논의**
    브라우저가 계산한 total을 /api/quotes가 검증 없이 저장합니다.

[4] PEAK_CALENDAR 해넘이 처리 → **기각**
    inRange가 이미 처리합니다:
      const inRange = (from, to) => (from <= to ? (mmdd >= from && mmdd <= to)
                                                : (mmdd >= from || mmdd <= to));
    from='12-20', to='01-03' 구간은 from>to 분기를 타서 정상 동작합니다.

[5] bizCount 실수 입력 → **부분 인정(경미)**
    Math.max(0, Number(...)||0)과 Math.min(bizCountRaw, participants)로 범위는
    잡히지만 정수화는 없습니다. <input type="number" min="0">에 step이 없어 2.5 입력이
    가능하고, 가중평균에 2.5명이 들어갑니다. 금액은 중간값이 나올 뿐 폭주하지 않습니다.

[6] 음력 연휴 날짜 → **인정. 그리고 당신 설명보다 심각합니다**
    PEAK_CALENDAR는 'MM-DD'로 매년 반복되는 구간인데 값은 2027년 기준 근사입니다.
    실측(방콕 기준, 항공·유류에 곱해지는 계수):
      2026-09-15 (평범한 날)      → ×1.22 "추석 연휴(근사)"   ← 근거 없는 과청구
      2026-09-25 (2026 실제 추석) → ×1.00                     ← 진짜 피크 놓침
      2026-02-06 (평범한 날)      → ×1.25 "설 연휴(근사)"     ← 근거 없는 과청구
      2026-02-17 (2026 실제 설)   → ×1.00
      2027-09-15 (2027 실제 추석) → ×1.22  ✓ (2027만 맞음)
      2028-01-26 (2028 실제 설)   → ×1.00
      2028-10-03 (2028 실제 추석) → ×1.00
    오늘은 2026-07-29이고 2026년 9월 출발은 약 7주 앞이라 예약 가능 구간입니다.
    코드 주석은 이렇게 적혀 있습니다:
      "좁은 구간을 쓰는 이유: 어긋난 해에 넓은 구간은 평범한 날을 과청구(위험)하지만,
       좁은 구간은 피크를 놓칠 뿐(소폭 과소추정, 안전)"
    이 주석의 안전 논리는 틀렸습니다. 좁아도 어긋난 해에는 평범한 날에 얹힙니다.

# 2라운드에서 답해 주실 것

Q1. [6]의 수정 방향. 제가 생각하는 안은 "연도별 실제 날짜 테이블"입니다.
    { year: 2026, from: '2026-09-23', to: '2026-09-27', factor: 1.22 } 처럼 절대 날짜로
    두고, 등록되지 않은 연도는 계수 1.0(피크 없음)으로 떨어뜨리는 방식입니다.
    - 이 방식의 문제점이 있으면 지적해 주세요.
    - "등록 안 된 연도는 1.0"이 맞습니까, 아니면 근사라도 적용하는 게 낫습니까?
      한국 아웃바운드 MICE 견적이라는 맥락에서 판단 근거와 함께 답해 주세요.
    - 연휴 구간을 실제 연휴일 기준 앞뒤 며칠로 잡아야 합니까? 출국 수요가 몰리는
      실제 패턴 기준으로요. 현재는 설 -2~+3일, 추석 -2~+2일 폭입니다.

Q2. [3] 클라이언트 계산 금액 문제의 현실적 대응.
    이 서비스는 계산 로직 전체(5,000줄)가 브라우저에 있고 서버에는 없습니다.
    서버에서 재계산하려면 엔진을 서버로 옮겨야 하는데 큰 작업입니다.
    - 실제 피해 시나리오를 구체적으로 써 주세요. 고객이 total을 조작해서 저장하면
      이 업체에 무슨 실질적 손해가 발생합니까? (견적은 상담 시작점이고 계약은 별도
      과정을 거칩니다.)
    - 그 피해 크기에 비해 합리적인 대응은 무엇입니까? 전체 재계산 말고 더 싼 방법이
      있다면 제시해 주세요.

Q3. 아직 못 본 영역에서 추가로 의심되는 것.
    아래는 이번에 검토하지 않은 부분입니다. 이 중 위험해 보이는 곳을 짚어 주세요.
    - 관리자가 요율을 고치면 DB에 저장되고, 고객 브라우저는 페이지 로드 시
      /api/rates를 fetch해 정적 표 위에 덮어씁니다. fetch가 느리거나 실패하면
      정적 기본값으로 계산됩니다(의도된 폴백).
    - 견적 결과를 고객에게 보여준 뒤 /api/quotes로 저장하는데, 저장 시점과 계산
      시점 사이에 요율이 바뀔 수 있습니다.
    - 환율은 매일 새벽 cron이 외부 API에서 받아 fx_rates에 저장하고, 목적지별
      기준환율(rate_fx_baseline) 대비 비율을 ±30%로 클램프해 원가 항목에 곱합니다.
      기준환율은 담당자가 그 목적지 요율을 저장할 때마다 '오늘 환율'로 재설정됩니다.

간결하게, 근거와 함께 답해 주세요.
