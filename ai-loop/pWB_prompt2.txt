[기각한 제안과 이유 — 반박하려면 근거를 대시오]
- "다국어 지원": 고객이 전부 한국 기업/개인이다. 지금 0순위가 아니다.
- "캘린더 통합": 팀원 6명이고 휴가는 카톡으로 공유된다. 시스템이 풀 문제가 아니다.
- "자동 알림": 이미 있다(문의·견적이 들어오면 관리자 대시보드 배지 + 미확인 카운트).
- "견적서 자동 저장/백업": 이미 있다(일 단위 DB 백업 + 클라우드 사본, 행 수까지 대조).
- "SERIAL/SEQUENCE로 날짜별 초기화": Postgres SEQUENCE는 **날짜별로 자동 초기화되지 않는다.**
  매일 ALTER SEQUENCE RESTART를 돌릴 크론이 필요한데 우리는 서버리스라 그 크론이 없다.
  이 제안은 그대로는 성립하지 않는다. 동의하는가?

[구체적 설계안 — 이것을 깨뜨리시오]

A. 번호 발급 (서버리스 동시 실행 안전)
   create table quote_seq (day date primary key, n int not null);
   -- 발급 시 한 문장:
   insert into quote_seq (day, n) values (current_date, 1)
     on conflict (day) do update set n = quote_seq.n + 1
     returning n;
   → 번호 = 'Q' + YYMMDD + '-' + lpad(n, 2, '0')
   질문:
   A1. 이 한 문장이 동시 요청에서 정말 안전한가? 어떤 격리 수준에서 깨지는가?
   A2. 하루 100건을 넘으면 lpad(2)가 무너진다. 자리수를 늘리면 옛 번호와 자릿수가 달라진다.
       무엇이 덜 나쁜가?
   A3. **발급은 성공했는데 그 뒤 insert가 실패하면 번호에 구멍이 난다.** 구멍이 난 번호를
       재사용해야 하는가, 그냥 비워야 하는가? 여행사 견적번호에서 구멍은 문제인가?
   A4. `current_date`는 DB 서버 시간(UTC)이다. 한국 오전 9시 이전에 발급하면
       **전날 번호**가 나온다. 어떻게 처리해야 하는가?

B. 견적서 링크의 수명 — 우리는 지금 만료가 **없다**
   우리 구조: 발급 시점의 금액·일정을 payload로 **통째로 저장**한다(서버가 소유).
   그래서 나중에 요율이나 대리점가가 바뀌어도 **옛 링크는 옛 금액을 그대로 보여준다.**
   질문:
   B1. 이게 맞는 설계인가? 여행사에서 "3개월 전 견적서 링크가 아직 그 금액을 보여준다"는
       것은 자산인가 부채인가? 근거를 대시오.
   B2. 만료를 넣는다면 무엇을 근거로 하는가(발급일 + N일? 출발일? 대리점가 유효기간?).
       만료된 링크는 무엇을 보여줘야 하는가 — 404인가, "기간이 지났습니다 + 담당자 연락처"인가?
   B3. 우리는 대리점이라 **적힌 값으로 팔아야 한다.** 고객이 만료 안내를 무시하고
       옛 링크를 근거로 그 금액을 요구하면? 화면 문구만으로 방어가 되는가?

C. 링크를 아는 사람은 누구나 본다
   현재 링크는 `estimate-view.html?id=mrx9l0xqhudmf1`. 인증이 없다.
   payload에는 **고객 담당자 이름·회사명**이 들어 있다(금액도).
   질문:
   C1. 이 정도 노출이 한국 개인정보보호법 관점에서 실제로 문제가 되는가?
       (이름+회사명+견적금액, 연락처는 payload에 없음) 과장하지 말고 답하시오.
   C2. id가 `Date.now().toString(36) + Math.random().toString(36).slice(2,8)`이다.
       즉 **시각(예측 가능) + 무작위 6자(36^6 ≈ 22억)**. 이걸 훑어 남의 견적서를 찾는 것이
       현실적인 위협인가? 숫자로 답하시오.
   C3. 만약 보완한다면, 견적서에서 **무엇을 빼는 것**이 가장 값이 큰가?

D. 견적서 대장에 반드시 있어야 할 것
   1라운드 답에 "연락처"가 있었는데 **우리 payload에는 연락처가 없다**(이름·회사명만).
   질문:
   D1. 연락처를 대장에 넣으려면 발급 시점에 새로 받아야 한다. 그 입력 부담을 감수할 만한가?
   D2. 고객이 전화로 말할 수 있는 정보만으로 역산했을 때, **최소한** 무엇으로 검색되어야
       하는가? 우선순위를 매기시오.
   D3. "당일 만료 견적 필터"를 제안했는데 우리는 만료 개념이 없다(B 참조). 재고하시오.

E. 편의 기능 — 6명이 쓰는 시스템에서 **자주 아플 것**만
   기각한 것 말고, 이 시스템의 실제 구조를 보고 다시 3개만 고르시오.
   참고: 담당자는 견적을 낸 뒤 **카톡/메일로 링크를 보낸다**. 고객이 답을 안 하면 잊는다.
   상태 관리는 quotes 테이블에 status(new 등)와 assignee가 있으나 **발급된 견적서
   (quote_shares)에는 상태도 담당자도 없다.**
